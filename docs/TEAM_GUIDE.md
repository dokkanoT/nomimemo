## 1. 何を作るのか（30 秒で）

**飲み会を「投稿」として記録して、あとから振り返れる Web アプリ**です。

- 飲み会ごとに「写真・参加者・話題タグ・メモ」を残す
- Instagram のような**タイムライン**で過去の飲み会を眺められる
- 「AWS」「就活」などで**検索**すると、その話をした飲み会が出てくる

使う技術：

| 種類 | 技術 | ひとことで |
|---|---|---|
| 画面 | Next.js + TypeScript + Tailwind CSS | React で画面を作る。見た目は Tailwind のクラスで書く |
| データ | Supabase | DB・ログイン・画像保存をまとめて提供してくれるサービス |
| 公開 | Vercel | GitHub に push すると自動でサイトが更新される |

## 2. 誰が何をやるか

```
┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
│  バックエンド (BE)  │   │   A さん（閲覧系）  │   │   B さん（入力系）  │
│   dokkanoT         │   │                    │   │                    │
├────────────────────┤   ├────────────────────┤   ├────────────────────┤
│ ・Supabase 準備     │   │ ・共通レイアウト    │   │ ・ログイン画面      │
│ ・DB の設計         │   │ ・共通 UI 部品      │   │ ・飲み会作成フォーム │
│ ・ログイン処理      │   │ ・タイムライン      │   │ ・写真選択          │
│ ・データ保存/取得   │   │ ・飲み会詳細        │   │ ・参加者/タグ入力   │
│ ・写真の保存        │   │                    │   │ ・編集/削除         │
│ ・検索処理          │   │                    │   │ ・検索画面          │
└────────────────────┘   └────────────────────┘   └────────────────────┘
       データの裏側            「見る」画面              「書く」画面
```

**A さん = 見る画面、B さん = 書く画面** と覚えてください。
こう分けると、2 人が同じファイルを同時にいじることがほぼなくなり、ぶつかりにくくなります。

担当の Issue はラベルで分かります：
- `担当:A` → https://github.com/dokkanoT/nomimemo/issues?q=is%3Aopen+label%3A%E6%8B%85%E5%BD%93%3AA
- `担当:B` → https://github.com/dokkanoT/nomimemo/issues?q=is%3Aopen+label%3A%E6%8B%85%E5%BD%93%3AB

### 触るフォルダの目安

| フォルダ | 担当 | 中身 |
|---|---|---|
| `app/`（タイムライン・詳細ページ） | A | 見る画面 |
| `app/events/new/`, `app/search/`, `app/login/` | B | 書く画面・検索・ログイン |
| `components/ui/` | **A** | ボタン・カードなどの共通部品 |
| `components/forms/` | B | フォーム用の部品 |
| `lib/`, `supabase/`, `proxy.ts` | BE | データまわり（触らなくて OK） |

> 💡 B さんが共通部品（ボタンなど）を欲しくなったら、A さんに頼むか、自分で作って PR を出して A さんにレビューしてもらってください。

## 3. バックエンド担当がいま何をしているか

**ひとことで：「2 人がデータの心配をせずに画面を作れる土台」を作っています。**

### 3-1. Supabase の準備（Issue #1）← いまここ

Supabase は「データベース」「ログイン機能」「画像置き場」がセットになったサービスです。
自分でサーバーを立てなくても、アプリからデータを保存・取得できます。

いま作っているもの：

| ファイル | 役割 |
|---|---|
| `lib/supabase/client.ts` | **ブラウザ側**から Supabase につなぐための入り口 |
| `lib/supabase/server.ts` | **サーバー側**から Supabase につなぐための入り口 |
| `proxy.ts` | ページを開くたびに「ログイン中かどうか」を確認・更新する仕組み |
| `.env.example` | 接続に必要な設定値（URL・キー）の**名前だけ**を書いたひな形 |

> 2 人はこのファイルを直接使うことは基本ありません。次の「データ取得の関数」を使います。

### 3-2. DB の設計（Issue #2）

データをどんな表に入れるかを決めます。イメージ：

```
飲み会 (events)
 ├─ 写真 (event_photos)        … 1 つの飲み会に何枚でも
 ├─ 参加者 (event_participants) … 人 (people) とつなぐ
 └─ 話題タグ (event_tags)       … タグ (tags) とつなぐ
```

あわせて「**自分の記録は自分しか見られない**」設定（RLS という仕組み）も入れます。

### 3-3. データ取得の関数とモック（Issue #3）← 2 人に一番関係ある

画面から呼ぶ関数を先に用意します。たとえば：

```ts
import { listEvents } from "@/lib/data/events";

const events = await listEvents(); // 飲み会の一覧がもらえる
```

最初は**モック（本物っぽいダミーデータを返す偽物）**として作ります。
なので 2 人は、DB が完成していなくても**画面作りを始められます**。
あとで中身を本物に差し替えても、**呼び出し方は変わらない**ので画面側の修正は不要です。

```
  [A/B さんの画面]  ──呼ぶ──▶  listEvents()  ──▶  最初: ダミーデータ
                                              ──▶  あとで: 本物の DB
                                   ↑ ここ（呼び出し方）は変わらない
```

### 3-4. その後

ログイン処理（#4）→ データ保存の本実装（#5）→ 写真（#6）→ 参加者・タグ（#7）→ 検索（#8）の順に進めます。

## 4. 2 人にやってほしいこと

### ステップ 0：GitHub の招待を受ける（いますぐ）

メールか https://github.com/dokkanoT/nomimemo/invitations から招待を承認してください。
承認したら **GitHub のユーザー名を教えてください**（Issue の担当者に設定します）。

### ステップ 1：手元で動かす

事前に入れておくもの：**Node.js 22 以上**、**Git**、エディタ（VS Code 推奨）

```bash
git clone https://github.com/dokkanoT/nomimemo.git
cd nomimemo
npm ci
cp .env.example .env.local
```

`.env.local` に入れる値（Supabase の URL とキー）は **BE 担当から個別に送ります**。
⚠️ この値は **GitHub に上げない・グループ以外に貼らない** でください（`.env.local` は自動でコミット対象外になっています）。

値を入れたら：

```bash
npm run dev
```

http://localhost:3000 が開ければ OK です。

### ステップ 2：データがなくても始められること（#3 のモックが出来るまで）

| A さん | B さん |
|---|---|
| #9 共通レイアウト・UI 部品（ヘッダー、ボタン、カードなど） | #12 ログイン画面の見た目 |
| タイムラインのカードの見た目を、仮の文字で作ってみる | #13 作成フォームの見た目（入力欄・ボタン） |

**スマホで見たときの見た目を優先**してください（このアプリはスマホで使われる想定です）。

### ステップ 3：モックができたら

BE 担当から「#3 終わったよ」と連絡が来たら、`lib/data/` の関数を使って画面にデータを流し込みます。
使い方は [DATA.md](DATA.md) にまとめています。

## 5. 作業の進め方（毎回これ）

```
① Issue を選ぶ → 自分を Assignee にする
② main を最新にしてブランチを作る
③ 作業してコミット
④ push して PR を出す（本文に closes #番号）
⑤ 誰かがレビュー → OK ならマージ
⑥ Issue が自動で閉じる 🎉
```

コマンド例（Issue #10 タイムライン画面の場合）：

```bash
git switch main
git pull
git switch -c feat/timeline        # ブランチ名は feat/やること
# … 作業 …
git add .
git commit -m "タイムライン画面のカードを作成"
git push -u origin feat/timeline
```

push したら GitHub に「Compare & pull request」ボタンが出るので、それを押して PR を作ります。
PR の本文に **`closes #10`** と書くと、マージ時に Issue #10 が自動で閉じます。

### ルール

- ✅ **main に直接 push しない**（必ず PR 経由）
- ✅ **PR は小さく**（1 つの Issue = 1 つの PR。1〜2 日で終わる大きさ）
- ✅ **CI（自動チェック）が緑になってからマージ**。赤なら `npm run lint` と `npm run build` を手元で試す
- ✅ PR を出したら Vercel が**プレビュー用 URL** を自動で作るので、それで見た目を確認できる
- ✅ 詰まったら **30 分悩んだら聞く**。Issue にコメントすると経緯が残って便利

## 7. よくある質問

**Q. Next.js の書き方を調べたら、ネットの記事と違う気がする**
A. このプロジェクトは **Next.js 16** で、古い記事と書き方が違うところがあります（例：`middleware` → `proxy` に名前変更）。
迷ったら `node_modules/next/dist/docs/` の公式ドキュメントを見てください。

**Q. `npm run dev` でエラーが出る**
A. まず `.env.local` に値が入っているか確認してください。空だと起動時にエラーになります。

**Q. 他の人とファイルがぶつかった（コンフリクト）**
A. 慌てずに相談してください。2 章の「触るフォルダの目安」を守っていれば、ほとんど起きません。

**Q. デザインはどう決める？**
A. A さんが共通部品と色を決め、B さんもそれを使う形にすると統一感が出ます。最初に 3 人で軽くすり合わせましょう。
